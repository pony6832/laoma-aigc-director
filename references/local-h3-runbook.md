# 地端 H3 製作手冊

在本機 ComfyUI 跑 MiniMax H3（或其他吃顯存的影片模型），遇到顯存問題、要拆成多鏡頭，或要驗收角色一致性時讀這份。提示詞欄位結構仍以 `h3-prompt-writing` 技能為準；本案鎖定條件仍以本技能為準。

改寫自 Rimagination 的 h3lite（MIT 授權，見 `H3LITE_LICENSE.txt`），已依本技能用語重寫並刪減；只取方法，不取它的模型組合與腳本。

## 錨點卡（任何模型都適用）

多鏡頭或角色會重複出現的案子，寫提示詞前先為每份參考素材記下四件事，並在所有鏡頭沿用同一組名稱：

| 欄位 | 內容 |
|---|---|
| 用途 | 身分、首幀、尾幀、姿勢、運鏡、風格、動作或聲音 |
| 保留 | 必須完整保留、部分保留，或只當弱參考 |
| 可變 | 允許變化的動作、運鏡、焦點或表情 |
| 禁止漂移 | 身分、服裝、記號、道具、背景、比例、聲音細節中不得改變的項目 |

- 每個角色只用一個固定名稱（例如 `Subject A`），不換別名；同一序列每一鏡的角色描述逐字相同。
- 一份主參考，加上每個新構圖一張延續或反拍關鍵幀。關鍵幀是錨點，不是另一個故事：服裝、光線、天氣、背景要先對齊主參考。
- 缺少必要參考時，問一個問題或講明替代做法，不可默默從「保留身分」退成純文字生成。
- 錨點卡存進案件 `04_shot_design/`，和逐鏡表一起鎖定。

## 首／中／尾幀驗收

能播放、有音軌的 MP4 不代表身分正確。每一鏡生成後抽首、中、尾三幀，對照錨點卡檢查身分、服裝與連戲，結果寫入 QC；身分漂移記為 `identity_drift`。圖生影片會重新生成首幀，所以和參考圖接近但不會逐像素相同；身分是驗收條件時要明確檢查，不能從「首幀是參考圖」推定。

## 一次生成就是一個連續鏡頭

H3 一次只產出一個連續鏡頭，在同一段提示詞裡要求「切到特寫再切回來」會糊掉或停住。要有真正的鏡頭涵蓋（建立鏡、過肩、反拍、揭示），就把場景拆成幾個鏡頭分別生成，再在剪輯接起來：

| 段落 | 用途 | 運鏡 |
|---|---|---|
| C1 | 建立鏡 | 中遠景雙人，慢推 |
| C2 | 過肩 A → B | 在 A 肩後，焦點在 B |
| C3 | 反拍 B → A | 在 B 肩後，焦點在 A |
| C4 | 揭示／全景 | 側面角度，交代空間 |

- 每段各做一張首幀。過肩或被遮擋的鏡頭，首幀仍要露出被遮角色的身分特徵（膚色、髮型、鬍子、服裝）；臉完全被肩膀擋住時，模型會自己發明一個新的人。這類首幀要拿清楚的雙人鏡頭當參考圖來生成，只靠文字鎖身分不夠。
- 只有在會揭露新資訊時才切鏡；資訊能留在同一構圖時，改用焦點、走位或運鏡。

### 用 ffmpeg 交叉淡化接段

所有段落先統一解析度、幀率，並確認都有音軌。淡化長度 `T`，各段長度 `d1, d2, …`：

```text
offset_1 = d1 - T
offset_k = offset_(k-1) + d_k - T   (k >= 2)
```

```powershell
ffmpeg -y -i C1.mp4 -i C2.mp4 -i C3.mp4 -filter_complex "[0][1]xfade=transition=smoothstep:duration=0.5:offset=<offset_1>[v01];[v01][2]xfade=transition=smoothstep:duration=0.5:offset=<offset_2>[v];[0:a][1:a]acrossfade=d=0.5[a01];[a01][2:a]acrossfade=d=0.5[a]" -map "[v]" -map "[a]" -c:v libx264 -pix_fmt yuv420p -c:a aac FINAL.mp4
```

交付前用 `ffprobe` 確認總長、幀率與影音兩軌都在。

## 人臉鏡頭的路線

| 目標 | 建議路線 |
|---|---|
| 物件、風景、卡通 | 文生影片即可 |
| 單鏡可辨識人物 | 圖生影片，首幀清楚；單人、正臉或四分之三側臉，髮型與服裝穩定 |
| 跨鏡同一人物 | 參考圖生影片（Ref2VA）；節點有註冊不代表路線可用，第一次要跑完整工作流並人工驗收身分 |

- 先驗證不說話時的臉部穩定，再加對白或口型。
- 快速轉頭、強烈表情、說話和大幅運鏡同時出現，會疊加身分風險；一鏡只放一兩樣。
- 人臉檢查只用提示詞改寫、現有首幀、抽幀與輕量媒體分析，不為了「人臉模式」自動加步數、加第二個模型或整段重生成。

## 顯存搶用診斷（Windows）

同一張顯卡上同時有 ComfyUI 和其他吃 CUDA 的程式（影片放大工具、另一個生成後端、遊戲串流）時，會出現「看起來有空、其實分配不到」的假空閒：

- 新版 Windows WDDM 驅動下，`nvidia-smi --query-compute-apps` 對每個程序常顯示 N/A，看不出誰佔著顯存。
- PyTorch 回報的可用顯存是樂觀估計；錯誤訊息可能寫著還有數 GB 可用，卻連幾十 MB 都分配失敗。
- 失敗有兩種樣子：明確的 `CUDA out of memory`，或沒有 OOM 字樣的存取違規（結束碼 `-1073741819`，即 `0xC0000005`）。後者很容易誤判成驅動或模型壞掉。
- ComfyUI 佇列清空後模型仍常駐顯存（實測可達約 10 GB）。佇列空不等於已釋放。

處理順序：

1. 看每個程序實際佔用：
   ```powershell
   (Get-Counter '\GPU Process Memory(*)\Dedicated Usage').CounterSamples | Where-Object CookedValue -gt 0 | Sort-Object CookedValue -Descending | Select-Object -First 8 InstanceName, @{n='MB';e={[int]($_.CookedValue/1MB)}}
   ```
   計數器路徑開頭的反斜線不能省。InstanceName 內含 PID，可對照工作管理員。
2. 確認對方閒置。ComfyUI 看佇列：
   ```powershell
   Invoke-RestMethod http://127.0.0.1:8188/queue | ConvertTo-Json -Depth 2
   ```
   `queue_running` 與 `queue_pending` 都空才算閒置；有工作在跑時先等它完成。
3. 釋放：正常關閉對方程式；ComfyUI 的常駐模型要重啟 ComfyUI 才會放掉。結束程序前先向使用者確認，不可直接砍正在運算的程序。
4. 重跑被擋下的工作。常發生時，送出前先檢查空閒顯存是否高於門檻，或讓常駐方加上 `--lowvram` 之類的限制。
